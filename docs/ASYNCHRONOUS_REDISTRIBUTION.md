# Asynchronous rainfall redistribution

## Purpose and scope

AOWIS-SERVER-HYDROLOGY can compute the static Fill–Spill–Merge-style
**volume redistribution** for a previously saved rainfall scenario in the
background. This prevents an HTTP request from waiting for the DEM, runoff
raster, and basin hierarchy to be loaded and processed.

The physical model is **unchanged**: this is a static, instantaneous volume
accounting approximation, **not** a hydraulic time simulation. The outputs
are basin-retained volumes and volumes leaving the analysis domain. They do
not include arrival times, discharge rates, inundation depths, or physically
resolved water levels. See [RUNOFF_REDISTRIBUTION.md](RUNOFF_REDISTRIBUTION.md)
for the assumptions and mass-balance equations.

## Preconditions

1. A completed terrain-analysis job must exist (`GET /v1/jobs/{job-uuid}`).
2. A rainfall scenario must already have been created for that job
   (`POST /v1/jobs/{job-uuid}/rainfall-scenarios`).
3. The job's original DEM, `basins.aowbin`, scenario manifest, and
   `runoff.f64` must still be readable and match their saved geometry.

A scenario is the **unit of computation**; requesting the same scenario
multiple times does not create duplicate concurrent calculations. The
background task has its own runtime UUID, while the analysis and scenario
UUIDs remain stable across restarts.

## HTTP workflow

All paths below are relative to the Hydrology server (default local port is
configured by the server, typically `8123`). Replace UUID placeholders with
real values from the preceding API requests.

| Operation | HTTP | Result |
|---|---|---|
| Submit or reuse | `POST /v1/jobs/{job-uuid}/rainfall-scenarios/{scenario-uuid}/redistribution` | `202 Accepted` for queued/running work; `200 OK` if a validated cache already exists |
| Poll | `GET /v1/jobs/{job-uuid}/rainfall-scenarios/{scenario-uuid}/redistribution/status` | `200 OK`, current task state and cache readiness |
| Read page | `GET /v1/jobs/{job-uuid}/rainfall-scenarios/{scenario-uuid}/redistribution?offset=0&limit=50` | `200 OK` when cached; `409 Conflict` if computation has not produced a valid cache |
| Cancel | `DELETE /v1/jobs/{job-uuid}/rainfall-scenarios/{scenario-uuid}/redistribution` | `202 Accepted` if cancellation was requested; `409 Conflict` if no task is active |

The HTTP **GET result endpoint never starts or performs computation**.
It reads the precomputed cache with bounded pagination. Clients should start
via POST and then poll the status endpoint rather than retrying result GETs.
This is intentional: a GUI map pan or a REST pagination request must not
silently start a long CPU-intensive analysis.

### Command-line example

```bash
BASE="http://127.0.0.1:8123/v1/jobs/JOB_UUID/rainfall-scenarios/SCENARIO_UUID"

# 1. Queue analysis. Repeating this does not queue another concurrent run.
curl -i -X POST "$BASE/redistribution"

# 2. Poll until state becomes "completed" and cache_ready becomes true.
curl -sS "$BASE/redistribution/status"

# 3. Retrieve only the needed basin page. These calls never recompute.
curl -sS "$BASE/redistribution?offset=0&limit=50"
curl -sS "$BASE/redistribution?offset=50&limit=50"

# Optional: stop queued or running work.
curl -i -X DELETE "$BASE/redistribution"
```

An example task/status object:

```json
{
  "id": "adf5cbe7-9dac-4cf1-8a80-9c8e255244e4",
  "job_id": "00000000-0000-4000-8000-000000000001",
  "scenario_id": "00000000-0000-4000-8000-000000000002",
  "state": "running",
  "error": "",
  "cache_ready": false
}
```

Those UUIDs illustrate the response shape; they are not real service objects.
The `id` field is the background task UUID or `null` if the service
recovered a completed result from disk without an in-memory task. All
AOWIS entity IDs that are generated by this API are UUIDs. Scenario
and analysis IDs are **not** reissued for repeated requests.

### States and interpretation

| State | Meaning | What the client should do |
|---|---|---|
| `not_started` | No current task and no valid cache; also used for a formerly completed task whose cache is invalidated | Submit POST |
| `queued` | Task accepted and waiting in the bounded worker queue | Poll status |
| `running` | Worker is reading sources, routing and/or writing the result | Poll status; optionally cancel |
| `cancel_requested` | Cancellation flag set, worker has not yet stopped | Continue polling |
| `canceled` | Worker stopped without publishing a new result | Submit POST again to retry |
| `failed` | Calculation failed; `error` describes the failure | Correct inputs/storage conditions and retry POST |
| `completed` | A valid cache is available (`cache_ready=true`) | Read paginated GET results |

The authoritative readiness indicator is `cache_ready`. It is calculated by
checking archive identity, geometry, checksum/shape validation of the header
and first record, and agreement with the saved scenario runoff total. A later
corrupt record can still be detected when that page is read. Derived cache
corruption never changes the saved rainfall scenario or DEM; submitting POST
again rebuilds it.

Cancellation is **cooperative**. It is checked while reading runoff cells,
during the core redistribution calculation and before publishing the archive.
Some filesystem operations (e.g., loading a large DEM) may not stop
immediately. A cancel request is not a promise that a concurrently finishing
valid cache will be removed; once published, a valid cache remains reusable.

### HTTP error handling

- `400 Bad Request`: malformed pagination or invalid identifiers/parameters.
- `404 Not Found`: unknown/incomplete analysis job (and source-loading errors
  carry their error message; do not mistake a missing scenario for success).
- `409 Conflict`: result is not ready, the eight-task queue is full, or there
  is no active task to cancel.
- `500 Internal Server Error`: unreadable, inconsistent, or otherwise invalid
  source data, or a filesystem/calculation failure.

Use the response `error` field to distinguish individual failures; the exact
HTTP mapping of an unknown scenario is not a stable typed error code yet.

## In-process C++ service

The `AOWIS::HydrologyService` library exposes these methods on
`AnalysisService`:

```cpp
QJsonObject startRainfallRedistribution(
    const QString &analysis_uuid, const QString &scenario_uuid, QString *error);
QJsonObject rainfallRedistributionStatus(
    const QString &analysis_uuid, const QString &scenario_uuid, QString *error) const;
bool cancelRainfallRedistribution(
    const QString &analysis_uuid, const QString &scenario_uuid, QString *error);
QJsonObject rainfallRedistributionReady(
    const QString &analysis_uuid, const QString &scenario_uuid,
    int offset, int limit, QString *error) const;
```

The pre-existing synchronous `rainfallRedistribution(...)` method remains
available to specialized in-process callers for backwards compatibility.
**It may block** and calculate a missing/invalid cache. Use the `Ready`
method for GUI/REST-style nonblocking behavior. Both methods share the
same cache format and physical calculation.

An embedding application **owns the service lifetime**. Its destructor
requests cancellation of outstanding tasks and joins the workers before
releasing its dependencies. The existing injected Map terrain reader and
any borrowed Map instance must outlive `AnalysisService`.

## Scheduling, memory and integrity

- A dedicated Qt `QThreadPool` with **one worker** performs redistribution.
  This prevents unbounded simultaneous DEM/runoff/hierarchy loads.
- At most **eight** background redistribution tasks may be active or queued
  per service instance. Additional requests receive a queue-full error.
- Requests for the same scenario are idempotent while queued, running, or after successful completion with a valid derived cache. A completed result is revalidated under the task-table lock before allocating another UUID, closing the completion window between the initial status check and the duplicate-task lookup. A missing, damaged, or stale cache is not reused; submitting again creates a new task.
- Concurrent caches are published atomically using Qt `QSaveFile`; clients
  never see a partially committed binary file.
- The existing process-local cache mutex serializes writers, including
  legacy synchronous calls. The cache-only reader does not acquire that
  long-running compute mutex.
- The per-scenario binary cache is *derived and disposable*; its integrity
  and invalidation are documented in
  [REDISTRIBUTION_CACHE.md](REDISTRIBUTION_CACHE.md).
- If the service is shut down or crashes, the current in-memory task state
  does not survive. A finished, valid cache **does** survive. After restart,
  status will say `completed` with `id: null` if the cache is valid,
  otherwise `not_started`; the client can submit again.

No progress percentage or ETA is exposed in this increment. Task state is
not yet a durable event/history record; persistent result files are the
source of truth after restart. Multi-process/distributed writer coordination,
timeouts, explicit prioritization, and metropolitan-scale performance
benchmarks remain future work.

## Checking correctness

The service regression tests cover cache-only reads, missing cache rejection,
background submission, duplicate-submission idempotency, finished-result
pagination, cache re-use after restart, and repeated successful builds in the
Debug and Release test suite. Core tests still verify the governing mass
balance:

\[
V_{runoff} = V_{stored\ in\ root\ basins} + V_{boundary\ outflow}
\]

Nested basin storage totals must **not** be added independently: a parent's
reported subtree volume already contains its children's storage.

This API does not create SWMM hydraulic routing, a flood hydrograph, a flooded
street polygon, or a spatial inundation-depth raster.
